# lowbit

Fused dequantize + GEMM kernels for low-bit LLM weight formats on x86 CPUs,
with runtime ISA dispatch, a tile-size autotuner, bit-exact tests and
benchmarks measured on the machine they were built on.

Three weight formats, one GEMM (`Y[M,N] = X[M,K] · W[N,K]ᵀ`, the `nn.Linear`
convention):

| format | weights | activations | inner product |
|---|---|---|---|
| **W4A16** | int4, group 128, fp32 scale per group, optional uint8 zero-point | fp32 | fp32 FMA, dequantized in registers via a per-group 16-entry table |
| **W4A8** | same int4 weights | int8, per-token scale (quantized inside the call) | AVX-512 VNNI `vpdpbusd` (u8×s8→s32), exact int32 per group, then fp32 rescale; AMX-INT8 `tdpbsud` path too |
| **MXFP4** | OCP Microscaling FP4: E2M1 elements, block 32, shared E8M0 power-of-two scale | fp32 | fp32 FMA, E2M1 decoded with `vpermps` from a per-block table |

The packed weights are never expanded to an fp32 matrix: each 16 packed bytes
are widened, decoded and consumed by FMAs (or dot-product instructions) in
registers.

## Why this is not just "call BLAS"

* **Formats that general BLAS does not have.** OpenBLAS and MKL's cblas GEMM
  take fp32/fp64 (and bf16/int8 in some builds); none takes group-wise int4
  with per-group scale and zero-point, int4×int8 with a per-group rescale inside
  the K loop, or OCP MXFP4. The only way to use them with BLAS is to
  dequantize first — the `numpy deq+mm` baseline below — which costs 8× the
  weight bytes plus the conversion. (oneDNN and llama.cpp/ggml have their own
  int4 paths; a measured comparison against ggml is below. We did not
  benchmark oneDNN.)
* **Verified bit-for-bit where bits are defined.** The W4A8 int32 group
  accumulators from every path (scalar, AVX2 `vpmaddubsw`, AVX-512 VNNI, AMX)
  are compared with `numpy` int64 arithmetic with `assert_array_equal`,
  including worst-case operands (codes 0/15, activations ±127/−128) that
  would expose `vpmaddubsw` saturation. The C activation quantizer is
  bit-identical to the numpy one. Floating-point paths are checked against a
  float64 reference with an error bound of `1e-5 · (|X|·|W|ᵀ)`.
* **Measured numbers, with the baselines you would actually use.** Every
  number below is generated from `results/bench.json` (a test fails if the
  README drifts from it), including the regimes where OpenBLAS wins.

## Quickstart

```bash
cd lowbit
pip install -e ".[test,bench]"      # numpy; pytest + threadpoolctl for tests/benchmarks
lowbit info                         # detected ISA, VNNI/AMX, OpenMP threads
pytest -q                           # ~10 s; builds the C library on first use
```

```python
import numpy as np, lowbit as lb

w = np.random.randn(4096, 4096).astype(np.float32)   # [N, K]
x = np.random.randn(1, 4096).astype(np.float32)      # [M, K]

w4 = lb.quantize_int4(w, asym=True)     # int4 g128 + fp32 scale + uint8 zero-point
mx = lb.quantize_mxfp4(w)               # OCP MXFP4

y1 = lb.gemm_w4a16(x, w4)               # fp32 activations
y2 = lb.gemm_w4a8(x, w4)                # int8 per-token activations (VNNI)
y3 = lb.gemm_mxfp4(x, mx)
y4 = lb.gemm_w4a16(x, w4, params="auto", threads=1)   # use autotuned tiles if cached
```

CLI:

```bash
lowbit tune --shape 1x4096x4096 --shape 16x11008x4096     # autotune, cache to ~/.cache/lowbit/tune.json
lowbit bench --out results --readme README.md --wait-idle 0.9   # full benchmark (~30-60 min)
lowbit bench --quick --out /tmp/lb                          # 2 shapes, a few minutes
lowbit report --results results --readme README.md          # re-render markdown from JSON
pip install -e ".[model]"                                   # + tokenizers, for a real model
lowbit e2e --readme README.md --wait-idle 0.9               # Qwen2.5-0.5B tokens/s + perplexity
lowbit e2e --tiny --out /tmp/lb-e2e                         # tiny random model, no download
LOWBIT_ISA=avx2 pytest -q                                   # force the non-AVX-512 path
```

How to read this (the commentary is written by hand; the tables are not):

* **Decode is memory-bound, and 4-bit wins because it moves 7.5× fewer
  bytes.** In the cold-cache decode table, OpenBLAS streams its 172 MiB of fp32
  weights at 15 GB/s on one core and 54 GB/s on four; the 4-bit kernels move
  22.8 MiB and finish 1.9–5.4× sooner even though they reach lower byte rates —
  the fp32-FMA decoders (W4A16, MXFP4) are still partly compute-bound on the
  decode, while W4A8 (integer dot products, no float decode at all) is the
  fastest path everywhere at M=1.
* **Naive dequantize-then-matmul is the worst option by far** (0.01–0.4× of
  fp32): numpy's dequantization is single-threaded and writes the full fp32
  matrix every call.
* **Where OpenBLAS wins:** at M=64 the fp32-activation kernels (W4A16,
  MXFP4) are at 0.9–1.0× of sgemm — the per-weight table decode is no longer
  amortized against memory traffic and sgemm is a better-blocked compute
  kernel. W4A8 still wins there (2.4–2.8×) because an int8 dot product does 4
  MACs per lane per instruction.
* **AMX** is 7–16× over sgemm at M=16–64 but slower than the VNNI kernel at
  M=1 (per-group tile store + rescale overhead dominates when the tile has one
  row).
* **The scalar C path** is 20–30× slower than the SIMD paths; it exists as
  a portable, easily-audited reference and fallback.
* **vs llama.cpp:** on ggml's own harness and its default CPU path, our W4A8
  VNNI kernel is ~2.2–2.9× ggml's Q4_0 at decode and our MXFP4 is ~1.1–2.7×
  ggml's MXFP4. Read the caveats in "What is real" before quoting this.
  **End to end the lead reverses:** with a real model, llama.cpp repacks Q4_0
  into its AMX path and decodes 1.1–1.8× faster than our best backend (W4A8),
  and prefills 2–5× faster (see "End-to-end" below).

## End-to-end: Qwen2.5-0.5B

`lowbit.model` runs a real LLM — Qwen2.5-0.5B, chosen because it is small
enough to evaluate four backends × 20k tokens on 4 cores, ships
`model.safetensors` + `tokenizer.json`, and is a plain Llama-style decoder
(RMSNorm, RoPE, GQA, SwiGLU; plus q/k/v biases and a tied LM head) — with every
linear layer routed through fp32 numpy or one of the lowbit kernels. The fp32
path was checked against Hugging Face transformers (below). `lowbit e2e`
fetches the pinned model revision (sha256-checked), measures, writes
`results/e2e.json` and regenerates this block. The committed numbers came
from separate speed and quality runs (they merge into one file):


How to read this (hand-written; the numbers above are generated):

* **Decode gets 2.4–4.2× from the 4-bit kernels, and W4A8 is fastest.** At
  one thread the model is kernel-bound: linear layers + LM head are 84–87 %
  of a 4-bit decode step (94 % for fp32), and the speedups (3.2–4.2×) are
  close to the isolated-kernel ones. At four threads the kernels finish so
  quickly that the per-token numpy/python work that does not parallelize —
  attention (13–15 %) and norms/RoPE/residuals/call overhead (14–16 %) —
  is ~30 % of each step, which caps the gain at 2.4–3.1×. So numpy overhead
  does **not** dominate at 0.5B, but it is what limits the 4-thread number.
* **The LM head matters at this size.** The tied 151936×896 embedding is
  27 % of the linear weights and 13–25 % of decode time; it is quantized
  like every other matrix here (see the quality ablation for what that costs).
* **Prefill is where these kernels do not help.** W4A16 and MXFP4 are at or
  below fp32 for 64- and 512-token prefill, as the kernel tables predict
  (the fp32-activation kernels are ≈ sgemm at M=64 and slower beyond); W4A8 is 1.6–2×
  fp32 on the 64-token prompt but below it at pp512 with 4 threads, where
  attention (kept on one OpenBLAS thread with the lowbit backends, see
  `Model.blas_threads`) is 25–38 % of the time. The AMX kernel, 7–16× sgemm
  at M ≥ 16, is not wired into the model.
* **vs llama.cpp** (a real engine, run with its own Q4_0 path — here its
  AMX-INT8 kernels): with fp32 weights our numpy harness is 9–15 % behind
  llama.cpp in decode (6.2 vs 6.8, 20.7 vs 24.4 tok/s), so the harness
  itself is reasonable; with 4-bit weights llama.cpp is 1.1–1.3× (1 thread)
  and 1.5–1.8× (4 threads; default / pure Q4_0) faster than our best (W4A8)
  decode, and 2–5× faster in prefill. The kernel-level lead over ggml in the table further up (measured
  on ggml's default non-repacked path) does not carry over end to end.
* **Quality: round-to-nearest group-128 int4 costs a lot on a 0.5B model.**
  With everything in 4 bits (LM head included) and the library's default
  symmetric absmax/7 quantizer, perplexity goes from 13.8 to 20.8 (W4A16),
  21.5 (W4A8, which adds int8 per-token activations) and 19.6 (MXFP4), and
  only ~66 % of next-token argmaxes match fp32; greedy continuations diverge
  within 0–19 tokens. This is the quantizer and format, not the kernels (they match
  the dequantized weights to fp32 rounding — see the tests): the ablations use
  the same kernels and recover much of it — asymmetric int4 17.5, the
  signed-max scale 17.8, and keeping the 136M-parameter LM head in fp32
  another ~1 PPL (best: 16.4, +19 %). llama.cpp's Q4_0 loses 12–17 % on the
  same text by its own measure; it uses blocks of 32 rather than 128. In an
  uncommitted probe on the first 4k tokens, symmetric fake-quantization with
  groups of 32 instead of 128 recovered more than half of the loss, but the
  int4 kernels here only support group 128.
* **Noise.** Backends are interleaved run by run, so slow phases of the
  shared VM hit all of them alike; the brackets give the spread within the
  session. In an earlier, discarded session that ran backends one after
  another, 1-thread numbers were 20–30 % lower while `/proc/stat` showed no
  other process busy (host-level interference we cannot see), so trust the
  ratios more than the absolute tokens/s.

## Design notes

**Packed layouts** (see `src/lowbit/csrc/lowbit.h`). Each weight row is
`Kp/2` contiguous bytes.

* int4, group 128: group `g` is 64 bytes; byte `j` holds element `128g+j` in
  its low nibble and `128g+64+j` in its high nibble. Codes are unsigned
  `0..15`, value `(q − z)·s`, `z = 8` when symmetric.
* MXFP4, block 32: block `b` is 16 bytes; byte `j` holds `32b+j` (low) and
  `32b+16+j` (high) — the same "j / j+half" split ggml's Q4_0 uses. Codes are
  E2M1 (sign, 2-bit exponent, 1-bit mantissa); the block scale is one E8M0
  byte, `2^(e−127)`.

The "j / j+half" split means a 64-byte load gives the low halves of the group
with one `vpand` and the high halves with one shift+`vpand`, and the matching
activations are two *contiguous* 64-byte loads — no shuffles for W4A8, no
permutation of X.

**Dequantization by table lookup.** A group or block has only 16 possible
values, so the fp32 kernels build a 16-entry table per (row, group) —
`(q − z)·s` for int4 (one sub + one mul per 128 weights), `e2m1(q)·2^(e−127)`
for MXFP4 (exact) — and decode 16 weights with one `vpmovzxbd` + one
`vpermps` (which only reads the low 4 index bits, so the low nibble needs no
mask). This replaced `cvtdq2ps` + an FMA per 16 weights and was worth ~1.5×
on the decode path. The AVX2 MXFP4 path decodes the magnitude with an
8-entry `vpermps` and xors the sign bit in.

**W4A8 and the u8×s8 trick.** `vpdpbusd` multiplies *unsigned* bytes by
*signed* bytes (4 at a time, into int32 lanes). Unsigned 4-bit codes are
therefore the natural `u8` operand and int8 activations the `s8` operand. The
zero point is removed algebraically:

```
Σₖ (qₖ − z)·aₖ  =  vpdpbusd(q, a)  −  z · Σₖ aₖ
```

`Σ a` per group is computed once per token while quantizing X, and
`−z·Σa` is seeded into lane 0 of the int32 accumulator, so the group total is
exact integer arithmetic (the test compares it bit-for-bit). This is the same
"offset correction" used when the *activations* are the unsigned side
(u8 = s8 + 128, subtract `128·Σw`), just with the roles swapped so no bias is
needed. Without VNNI, the AVX2 path uses `vpmaddubsw` (u8×s8 → s16 pairs):
it saturates, but `2·15·128 = 3840` per pair and four such vectors add to
15360 < 32767 before `vpmaddwd` widens — exact again. The int32 group sum is
then converted to fp32 and scaled by the group's weight scale; the per-token
activation scale is applied once at the end.

**AMX path (bonus).** `tdpbsud` computes a 16×16 int32 tile from signed A
(activations, straight from the quantized X with stride K) and unsigned B
(weight codes). B must be in the "VNNI" layout (4 consecutive k per column),
so this path uses a one-time repacked weight layout (`formats.pack_amx`, 1 KiB
per 16 rows × 128 k, nibble-packed); each group is unpacked with `vpand`/
`vpsrlw` into two B tiles in L1, multiplied, the C tile stored and rescaled
with the same zero-point identity. The per-group rescale (every 2 tile ops) is
the bottleneck, which is why AMX wins at M≥16 and loses at decode.

**Tiling, threads, autotuner.** The driver splits N into tiles of `nb` rows
distributed over OpenMP threads (dynamic schedule, so a preempted core does
not stall the GEMM), optionally blocks K by `kb`, and calls an `mr×nr`
register-blocked micro-kernel (11 shapes compiled per ISA from one
`always_inline` body; each (row, col) pair keeps two accumulators so a 1×1
tile is not FMA-latency bound). Software prefetch runs 1 KiB ahead on the
weight stream (+25–40 % on cold-cache decode). `lowbit.tune` searches
micro-tile × `nb` × `kb` × loop order in two stages (~40–150 configurations,
min of 3–5 runs each) and caches the winner per (kernel, ISA, threads, M, N, K)
and CPU model in JSON. Across the 96 tuned (kernel, ISA, threads, shape)
combinations in `results/tune_cache.json` the tuned tiles are a median 1.18×
(max 3.6×) faster than the library defaults.

**Dispatch.** `dispatch.c` is compiled with baseline flags; each ISA lives in
its own translation unit compiled with only its own `-m` flags
(`kern_avx2.c`, `kern_avx512.c`, `kern_vnni.c`, `kern_amx.c`) and is only
called after `__builtin_cpu_supports` / CPUID (+ the Linux
`ARCH_REQ_XCOMP_PERM` request for AMX tile state). `LOWBIT_ISA=scalar|avx2|avx512`
caps the ISA (never raises it). W4A8 on an AVX-512 CPU without VNNI falls back
to the AVX2 kernel. The portable scalar path is plain C built with
`-fno-tree-vectorize`, so it is an honest scalar baseline.

**Build.** No build dependencies beyond a C compiler: the library is compiled
lazily on first import (`src/lowbit/_build.py`) into `src/lowbit/_build/`
(or `~/.cache/lowbit`), keyed by a hash of the sources and flags, and loaded
with `ctypes`. `make lib` forces it. OpenMP is used when the compiler has it;
the AMX unit is optional (skipped if the compiler lacks `-mamx-int8`).

**Constraints** (enforced in `formats.py`, tested with odd shapes):
any M, N, K ≥ 1. K is padded to a multiple of the block (128 for int4, 32 for
MXFP4); a partial last group is quantized from its real elements only, padded
codes decode to exactly 0 and X is zero-padded, so padding never changes the
result. Int4 zero-points are integers (uint8) so W4A8 stays exact. Activation
quantization is per token, symmetric, round-half-to-even (`np.rint`) and
clipped to ±127. MXFP4 follows OCP MX v1.0: shared exponent
`floor(log2(amax)) − 2`, round-to-nearest-even on E2M1, saturating to ±6.

## What is real and what is not

* **CPU only, one machine.** All numbers are from a 4-vCPU cloud VM (Intel
  Xeon @ 2.1 GHz with AVX-512, VNNI and AMX) that other workloads were sharing
  during the session. The benchmark waits for ≥90 % idle CPU before each block,
  measures other tenants' CPU time during every measurement (from `/proc/stat`
  minus our own) and re-measures when they used more than 0.25 cores; the
  residual is recorded per row (`other_tenant_cores`). Treat
  multi-threaded numbers as noisier than single-threaded ones.
* **The LLC on this VM is reported as 260 MiB**, so even the fp32 weight
  matrices can be cache-resident in the "hot" runs. The "cold" decode runs
  rotate through enough weight copies (> 2× LLC) to force DRAM traffic; they
  are the ones that model real decode.
* **No GPU, no Triton/CUDA.** Nothing here runs on a GPU.
* **The llama.cpp comparison is narrow.** It uses ggml's own
  `test-backend-ops perf` harness on its default CPU buffer path
  (`vec_dot q4_0 × q8_0`, MXFP4), built from source in this session with
  `-DGGML_NATIVE=ON` plus a one-line patch to set the thread count. It does
  *not* exercise ggml's repacked `Q4_0_8x8` or AMX extra-buffer paths that
  `llama-cli` would use with a real model, which are likely faster. Q4_0 is
  also a different format (block 32, fp16 scale) from our group-128 int4.
  If `results/llamacpp.json` is absent, no comparison was run.
* **The end-to-end model is a numpy reference, not an inference engine.**
  `lowbit.model` is ~400 lines of numpy around the kernels: fp32 activations
  and KV cache, one python call per op, no fused attention, no graph. Its
  tokens/s measure what the kernels buy *inside that harness*; they are not
  what the kernels would give inside llama.cpp or a C++ runtime, and the
  llama.cpp row in the End-to-end table (a real engine with its own Q4_0
  kernels) is the honest upper reference. Only one model (Qwen2.5-0.5B) and
  one text sample (~20k tokens of WikiText-2 test, not the full split) were
  evaluated; on 20k tokens the absolute perplexity has a standard error of
  roughly ±2 % (llama-perplexity reports ±2.7 % on the half-window scoring of
  the same text). Backends are compared on identical tokens, which is much
  tighter, but differences of a few tenths between ablations should not be
  over-read.
* **No calibration.** The quantizers are round-to-nearest (no GPTQ/AWQ), and
  the LM head is quantized too; the perplexity numbers are for exactly that,
  and on this model they show a large loss (see End-to-end).
* **Where numpy wins.** For compute-bound shapes (larger M) OpenBLAS's
  fp32 sgemm is a highly tuned kernel; the W4A16 and MXFP4 paths still pay a
  decode cost per weight that sgemm does not. See the tables: the honest
  story is "large wins when bytes matter (decode) and when integer dot
  products replace fp32 FMAs (W4A8), smaller or no wins otherwise".

## Tests and CI

```bash
# CI (ubuntu-latest; no AVX-512 needed — tests cover whatever the CPU has)
sudo apt-get install -y build-essential     # gcc + libgomp (already on GitHub runners)
pip install -e "lowbit[test]"
cd lowbit && pytest -q                      # uses the best ISA the runner has
LOWBIT_ISA=avx2 pytest -q                   # force the AVX2 fallback
LOWBIT_ISA=scalar pytest -q                 # force the portable scalar path
```

What the tests cover: nibble packing layout; int4 (sym/asym) and MXFP4
quantize→dequantize bounds, exactness on representable grids, E2M1 tie
rounding and saturation, E8M0 decoding; every kernel × every ISA the CPU
supports × 5 tile configurations (including K blocking and both loop orders)
× 7 shapes (1×1×1, odd M/N, K = 127, 129, 300, 1000, 4128) against the numpy
reference; W4A8 and AMX int32 accumulators bit-exact; C vs numpy activation
quantizer bit-exact; forced `LOWBIT_ISA` fallbacks in a subprocess; the
autotuner cache; the CLI; and that the README/RESULTS.md numbers are exactly
what `results/bench.json` renders to. For the model (`tests/test_model.py`,
tiny random configs, no downloads): the numpy forward pass against a naive
per-head float64 reference (GQA, untied head, no-bias variants), KV-cache
decode and chunked prefill equal to a full-sequence forward, greedy generation,
the bf16 safetensors loader, each 4-bit backend close to fp32 and exactly the
library GEMM on its quantized weights, `lowbit e2e --tiny` through the CLI,
and that the End-to-end README block is exactly what `results/e2e.json`
renders to.

## Next steps

* Port the kernels to Triton/CUDA (the table-lookup decode maps to
  `__byte_perm`/`prmt` or shared-memory LUTs; W4A8 to `dp4a`/IMMA).
* Make the AMX path competitive at decode: amortize the per-group rescale
  (e.g. rescale two groups per tile store, or fold scales into activations for
  symmetric weights) and keep B tiles pre-unpacked for M ≥ 64.
* Upstream the group-128 int4 × int8 VNNI kernel and the MXFP4 table decode to
  llama.cpp/ggml as a CPU repack path, and benchmark against its repacked
  Q4_0_8x8 and AMX paths with a real model (`llama-bench`).
* Quality: a group-32 int4 variant of the kernels, an 8-bit LM head, and
  calibrated quantization (GPTQ/AWQ), measured with the same harness.
* Route prefill (M ≥ 16) through the AMX kernel in `lowbit.model`.
* Move the per-token work of `lowbit.model` out of python (fused
  RMSNorm/RoPE/attention in C) so that end-to-end decode is bound by the
  kernels rather than by numpy call overhead.
